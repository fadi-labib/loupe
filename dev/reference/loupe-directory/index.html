    The .loupe/ directory¶

    Everything Loupe touches in your repo lives under .loupe/. This page documents every file and subdirectory — what it is, who writes it, who reads it, when it changes. The full schemas for the machine-readable artefacts live in Schemas; this page is the layout map.

    Tree¶

    .loupe/
├── config.yaml                       # operator config (human-managed)
├── context.md                        # product brief (human-authored, agent proposes patches)
├── knowledge.yaml                    # persistent knowledge graph (lens-promoted facts)
├── threat-model.md                   # narrative threat model (ThreatLens-authored)
├── threats.yaml                      # machine-readable threats (ThreatLens)
├── mitigations.yaml                  # machine-readable mitigations (ThreatLens)
├── sbom.cdx.json                     # CycloneDX SBOM (tool-generated: Syft)
├── vex.json                          # OpenVEX statements (ThreatLens; not_affected needs human OK)
├── decisions/
│   └── D-YYYY-MM-DD-<slug>.md        # ADR-style risk acceptances (human-authored)
├── runs/
│   └── YYYY-MM-DDTHH-MM-SS-ffffffZ-run-<id>.json   # hash-chained audit trail
└── .proposed/
    └── <any-protected-path>          # agent proposals for human review

    File-by-file¶

    config.yaml — human-managed¶

    The operator's configuration. Schema rendered live from LoupeConfig at Config reference. Not in agent_writable_paths; the agent reads but never writes. Changes go through normal PR review.

    context.md — human-authored, anti-hallucination anchor¶

    The product brief: what the product does, who its users are, what assets matter, what threats are out of scope. Every lens prompt includes this as the stable prefix so the LLM cannot wander. Parsed by ProjectContext.from_markdown(); see ProjectContext for the six required sections and the BulletItem shape.

    The agent cannot edit context.md directly. It can only propose_patch into .proposed/context.md for a human to merge.

    knowledge.yaml — lens-promoted facts, persistent across runs¶

    The cross-run knowledge graph. Scaffolded as empty (schema_version: 1, empty lists) on loupe init. Lens runs that produce high-confidence Facts (corroborated by a human decision or two independent runs) promote them into this file's assets, elements, decisions, and cross_references sections. Safe to delete to reset; the next run starts from an empty graph.

    Schema: KnowledgeGraph. Asset IDs match A-NNN, element IDs E-NNN, decision IDs D-YYYY-MM-DD-<slug>, fact IDs F-NNN.

    threat-model.md — narrative for auditors¶

    The prose threat model an auditor would read. ThreatLens authors and maintains it; cross-references threats by T-NNN ID into threats.yaml. Paired with the machine-readable file so engineers and auditors can each read the format that suits them, and the agent's job is to keep them in sync.

    threats.yaml — machine-readable threats¶

    Index of STRIDE-categorised threats with stable T-NNN IDs. Each threat links to a system element, severity, status, mitigation IDs, CWE/CAPEC references, and a rationale. Schema: see Threat. Status transitions are humans-only past proposed.

    mitigations.yaml — machine-readable mitigations¶

    Index of mitigations with stable M-NNN IDs. Each mitigation references the threats it addresses and the evidence (code path, test, doc) that demonstrates it. Schema: see Mitigation.

    sbom.cdx.json — CycloneDX SBOM, tool-generated¶

    The Software Bill of Materials in CycloneDX 1.6 JSON format. Generated by the configured SBOM capability backend (default: Syft); the LLM never authors this. The capability registry caches the SBOM once per run so every lens reads the same value from the blackboard.

    vex.json — OpenVEX vulnerability statements¶

    Per-CVE impact statements in OpenVEX 0.2 format. ThreatLens generates statements with status affected or fixed (mechanical CVE matches). Statements with status not_affected are drafts only — they require human approval through propose_patch because "we are not affected because X" is an analytical judgement, not a mechanical claim.

    decisions/D-YYYY-MM-DD-<slug>.md — human-authored risk acceptances¶

    ADR-style records for risks the team has explicitly chosen to accept, defer, or accept-with-mitigation. ID format D-YYYY-MM-DD-<slug> (matching the filename pattern in the tree above). Authored by humans and signed by a human identity; the agent can only draft into .proposed/decisions/ for review. Cross-referenced by Decision entries in knowledge.yaml.

    runs/<timestamp>-<id>.json — hash-chained audit trail¶

    One file per Loupe invocation. Records inputs (hashed diff, hashed context.md), which lenses were considered and which ran, models used, tokens consumed, cost estimate, artefacts written, and the SHA-256 hash chain pointer. Filename uses microsecond-precision UTC so lexical sort matches chain order.

    loupe verify walks the chain and exits non-zero if any record's prev_run_hash doesn't match the previous record's self_hash. Schema: see RunRecord. Verification recipe: see Verification.

    .proposed/<path> — agent proposals awaiting human review¶

    The agent's propose_patch tool writes drafts here when the target path is not in agent_writable_paths (e.g., context.md, decisions/*, config.yaml). A human reviews the draft and decides whether to apply it. The .proposed/ directory is never auto-merged.

    Who writes what¶

    Path Writer Notes
    config.yaml Human only Agent reads, never writes.
    context.md Human (or proposed) Agent uses propose_patch → .proposed/context.md.
    knowledge.yaml Loupe-core (promotion) Lens facts are promoted by the platform, not by the lens directly.
    threat-model.md ThreatLens Via write_agent_artifact. In agent_writable_paths.
    threats.yaml ThreatLens Same.
    mitigations.yaml ThreatLens Same.
    sbom.cdx.json Tool (Syft) Deterministic; the LLM never writes this.
    vex.json ThreatLens + human affected/fixed auto; not_affected requires human OK.
    decisions/*.md Human only Agent uses propose_patch → .proposed/decisions/.
    runs/*.json Loupe-core Written at end of every invocation; hash-chained.

    Allow-list vs proposal allocation¶

    The Layer 1 path boundary (see Verification §1) splits paths into two buckets:

    • Agent-writable — listed in config.yaml's agent_writable_paths. The agent's write_agent_artifact tool writes directly here. Default set: threats.yaml, mitigations.yaml, threat-model.md, vex.json, sbom.cdx.json, runs/**.
    • Protected — anything else. The agent must use propose_patch, which routes the write to .proposed/<original-path> for human review. Includes context.md, decisions/*.md, config.yaml, knowledge.yaml.

    The boundary normalises paths and rejects any path containing .. regardless of the allow-list. Absolute paths are allowed only if explicitly listed.

    What lives outside .loupe/¶

    • The repo's source code (packages/, src/, wherever your project keeps it) — Loupe reads via the diff but never writes.
    • CI configuration (.github/workflows/) — managed by humans; the loupe-action wrapper is documented at Contributing.
    • .git/ — read-only to Loupe.
    • VCR cassettes for tests — committed under packages/*/tests/cassettes/, not under .loupe/.
